# План развития ICO Toolkit по подтверждённым решениям

> Переработано по приложенному 999-строчному плану после сверки с текущей
> реализацией. Это приоритизированный roadmap, а не утверждение, что задачи ниже
> уже выполнены или что будущие задачи гарантированно решатся.

## Цель

Повысить долю **самостоятельно найденных и независимо подтверждённых** решений
на незнакомых файловых CTF-задачах. Инструмент остаётся без LLM/облачного ИИ,
офлайн по умолчанию и сохраняет доказательства происхождения каждого ответа.
Главная метрика — точные hash/checker-подтверждённые ответы на независимом
holdout; число установленных пакетов, строк-кандидатов и синтетических тестов
само по себе качеством решателя не считается.

что поддержанные задачи не сломались, но не входят в независимую оценку, если
их ответы уже использовались при разработке task-specific профилей.

## Решение по приложенному плану

| Идея исходного плана | Решение | Причина |
| --- | --- | --- |
| Автоматически определять формат, применять подходящие обработчики и связывать производные данные с источником | Сохранить как базовый принцип | Уже поддерживается реестром солверов, отчётами и SQLite evidence store |
| Ограничивать время, память, вывод, глубину и число файлов; не останавливать весь прогон при сбое одной утилиты | Сохранить, улучшать только по измеренным сбоям | Основная инфраструктура уже есть в solver limits и subprocess runner |
| Использовать хэшированный кэш и возобновлять дорогую работу | Сохранить | Кэш и content-addressed evidence store уже существуют |
| Сначала быстрые проверки, тяжёлые инструменты запускать по признакам | Сохранить и проверять метриками | `fast/full` и type-matched профили уже есть; нужно измерять их отдачу |
| Проверить и распределить все 31 проекта по `auto`, `manual`, `benchmark` и `skip` | Сохранить и выполнить | Полная матрица теперь находится в `TOOL_CATALOG.md`; не запускать каждый инструмент на каждом файле |
| Unblob, Binary Refinery, RsaCtfTool, FLOSS, capa и Dissect | Подключить к узким файловым сигналам | Unblob имеет ресурсные пределы; Refinery запускает Base32/Base58/Base64/Base85/hex/URL units; RsaCtfTool применяет только пять офлайн-атак к найденной паре ключ/ciphertext; FLOSS/capa выполняют статический анализ; Dissect qfind проверяется локальной fixture |
| SageMath, `crypto-attacks` и fpylll | Переносить методы по доказанным пробелам | Håstad broadcast и shared-prime batch-GCD уже встроены; fpylll/SymPy теперь решают один явно параметризованный RSA known-prefix small-root случай. SageMath не установлен: `brew info --cask sagemath` сообщает, что такого cask нет; остальные lattice-атаки требуют отдельных проверенных постановок |
| RSA shared-prime batch-GCD из `crypto-attacks` | Подключён как узкий межфайловый solver | Соединяет только явно индексированные `n_i/e_i/c_i`, возвращает plaintext лишь после RSA round-trip; позитивный, отрицательный и parser fixtures проходят, независимый corpus ещё не подтвердил прирост |
| CyberChef Magic и повторная реализация общего движка преобразований | Не дублировать существующие части | CyberChef и ограниченные преобразования уже подключены; новый путь добавлять лишь при воспроизводимом пропуске |
| Katana и Aperi'Solve как новая основа | Katana признать автоматическим CTF checklist-решателем; интегрировать выборочно, не запускать весь runner. Aperi'Solve оставить только локальным ориентиром | README Katana прямо предупреждает о SQLi/LFI, web-shell upload и RCE-проверках, а setup тянет legacy-зависимости. Чистые текстовые методы теперь добавлены отдельно и включаются только по явным словам задачи; весь framework не нужен для file-only режима |
| angr symbolic execution и Z3 | Реализован ограниченный stdin-профиль; расширять только после независимых бинарных checker-фикстур | Изолированное окружение установлено; профиль требует статические success/failure сигналы и зависимость найденного пути от stdin. Следующий gap — поддержка дополнительных архитектур и корректных input API без ложных кандидатов |
| SageMath/fpylll lattice attacks | Добавлять по воспроизводимому crypto-gap | fpylll и SymPy доступны в analysis-runtime; bounded Coppersmith known-prefix профиль добавлен и проверен на точном round-trip fixture. SageMath не установлен; HNP и другие lattice-атаки остаются отдельными задачами |
| Ghidra/angr/capa, FLOSS, PWN, volatility, TShark, stego и disk-forensics | Сохранить выборочно и по сигнатуре/условию | FLOSS/capa и Dissect qfind теперь имеют профили; тяжёлый blanket-run медленнее и добавляет шум |
| AFL++, локальные процессы, fuzzing и динамический запуск бинарников | Убрать из default; рассматривать как отдельный sandbox-этап | Статический `payload-ready` не равен флагу; запуск недоверенного файла требует изоляции и конкретной гипотезы |
| ffuf/sqlmap/nmap/HTTP discovery и другие активные web-проверки | Оставить только за явным allowlist локальной/разрешённой цели | Такие утилиты не решают файл сами по себе и не должны ходить на платформу или произвольные хосты |
| Словари, John/Hashcat, FactorDB и автоматический поиск ключей | Удалить слепой массовый запуск | Подбирать только значения, выведенные из условия, при разрешённых правилах и ограниченном бюджете; флаг brute force не использовать |
| Независимый hash-only holdout и слепая проверка | Сохранить и сделать главным критерием | Это наиболее сильное предложение плана; текущий smoke test ещё не даёт такой оценки |
| Отчёт причин нерешения, таймингов и ручных блокеров | Сохранить и расширить | Такой отчёт подсказывает, где менять алгоритм и когда задача неразрешима только по имеющимся файлам |

## План работ

### P0. Зафиксировать воспроизводимый baseline

**Файлы:**

- Создать `docs/superpowers/reports/2026-09-28-solver-baseline.md`.
- При необходимости обновить `scripts/run_corpus_matrix.py` и его тесты.
- Не менять solver-логику в этом шаге.

**Шаги:**

1. Запустить `./verify.sh` на текущем дереве и записать число тестов, пропуски,
   проверки CLI, длительность и причину каждого сбоя.
2. Для каждого доступного локального корпуса сохранить commit/hash источника,
   точную команду, чистый каталог отчёта, длительность и сводку состояний:
   `hash-verified`, `checker-verified`, `candidate`, `candidate-review`,
   `payload-ready`, `requires-authorized-session`, `unsupported`, `failed`.
3. Отдельно посчитать false positives, долю кандидатов, подтверждённых внешней
   проверкой, время до первого полезного результата и итоговое время.
4. Отметить для каждой задачи, достаточно ли приложенных артефактов: значение
   из случайного runtime, ответ сервиса или отсутствующий файл нельзя записывать
   как ошибку алгоритма, если этих данных нет в наборе.

**Проверки и критерий приёмки:**

- `./verify.sh` завершается успешно либо baseline явно фиксирует существующий
  отказ и его воспроизводящий тест.
- Один и тот же corpus дважды даёт одинаковые значения и task IDs; отличаться
  могут только тайминги и временные пути.
- Отчёт не называет `candidate`, внешний write-up или `payload-ready`
  подтверждённым решением.

### P1. Превратить hash-only scorer в полезную blind-оценку

**Файлы:**

- Изменить `scripts/holdout_benchmark.py` и `tests/test_holdout_benchmark.py`.
- Закрытые corpus и manifest хранить вне репозитория; не добавлять их в git.

**Шаги:**

1. Сохранить уже имеющиеся запреты plaintext-ответов и проверку manifest hash.
2. Добавить в hash-only scorecard итоги по `family` и `difficulty`, список
   пропущенных задач и task-level state без раскрытия правильных ответов.
3. Добавить `manifest_sha256`, solver revision, corpus revision, длительность,
   число ложных кандидатов и дубликатов в отчёт сравнения.
4. Убедиться, что solver запускается только на входном корпусе; scorer читает
   manifest после прогона. У тестового процесса нет пути к исходным write-up,
   answer-файлам или приватному manifest.
5. Собрать отдельный challenge-shaped набор: 3 истории × 5 категорий
   (`web`, `pwn`, `forensics`, `reverse`, `crypto`), 15 подзадач, с уровнями
   Easy/Medium/Hard, распределёнными по семействам. Использовать фиксированные
   архивы/коммиты и независимые checker/hash; хранить ответы отдельно.

**Проверки и критерий приёмки:**

- Unit-тесты проверяют plaintext rejection, неверный хэш, дубликаты, неизвестный
  task ID, пропуски и разрезы scorecard по семействам/сложности.
- Smoke-тест `verify.sh` остаётся, но помечен только как проверка скорера.
- Главная цель для этой выборки — **не менее 10/15 точных hash/checker-решений**,
  минимум 2/3 в каждом семействе и отсутствие ложных значений в actionable
  списке. Не достигнутый порог сообщает о gap; он не ослабляется подгонкой
  генератора под текущий solver.
- Рядом с 10/15 показывать исходный `N` и Wilson 95% интервал; маленькая
  выборка не считается вероятностью результата на любом будущем финале.

### P2. Закрывать только реальные провалы holdout

**Файлы:** выбирать после P0/P1; в первую очередь один из `ico_universal_*.py`,
`ico_task_solvers.py`, `ico_prompt_solvers.py` или `ico_tool_adapters.py` и его
тесты. Не создавать новый общий framework.

**Цикл на один gap:**

1. Выбрать провал, который повторился и имеет достаточные локальные артефакты.
2. Сохранить обезличенный минимальный reproducer, конкретный сигнал и ожидаемый
   evidence state; добавить позитивную, отрицательную и malformed-input фикстуру.
3. Проверить, что причина — отсутствие алгоритма/адаптера, а не неподходящая
   цель, недостающие файлы, недоступная optional-зависимость или ошибка среды.
4. Реализовать один минимальный solver/adapter. Новую программу подключать,
   только если она даёт уникальную способность, которую не покрывает текущий
   in-process код или доступный инструмент.
5. Перезапустить соответствующую часть blind holdout и известные regression
   corpora; записать дельту подтверждённых решений, false positives, время,
   память и число новых ручных блокеров.

**Критерий приёмки:**

- Изменение даёт хотя бы один новый точный ответ на закрытом holdout либо
  существенно убирает false positive/ошибку, не ухудшая остальные корпуса.
- Для тяжёлой интеграции выигрыш на holdout подтверждён после холодного запуска;
  сама доступность `--help` не считается полезным результатом.
- Если нет прироста, изменение откатывается или остаётся выключенным по
  умолчанию; каталог инструментов не расширяется ради числа.

### P3. Разнести статический solver и разрешённый динамический режим

**Файлы:** сначала отдельный design note; затем, только при наличии подходящих
тестовых локальных сервисов, `ico_active.py`, CLI и `tests/test_ico_active.py`.

**Шаги:**

1. Оставить файл-only `ico-solve` офлайн по умолчанию.
2. Для задач, которым нужны runtime-секрет, oracle, авторизация или ответ сервера,
   возвращать `requires-authorized-session` вместе с тем, чего именно не хватает.
3. Если задача включает сервис, добавить opt-in режим только для явно
   allowlisted localhost/container endpoint или адреса challenge-instance,
   указанного для этой задачи. Задать разрешённые порты, лимит запросов,
   deadline, логирование и запрет на платформенный/control-хост; проверить на
   тестовом локальном сервере до разрешённого challenge-instance.
4. Challenge-бинарники запускать только в отдельной одноразовой sandbox-среде
   без доступа к пользовательским данным; сетевой доступ по умолчанию выключен.
5. Не отправлять найденный флаг на платформу автоматически.

**Проверки и критерий приёмки:**

- Unit/integration-тесты доказывают отказ для платформы ICO, произвольного
  хоста и неразрешённого порта до первого сетевого запроса; разрешён только
  точный host/port из allowlist задачи.
- Разрешённый локальный fixture-server подтверждает только свой тестовый ответ.
- Локальный payload или успешно собранный exploit остаётся `payload-ready`, пока
  тестовый checker не подтвердит результат.

### P4. Оптимизировать скорость по полезной отдаче

**Файлы:** `scripts/benchmark_ico_solve.py`, соответствующие тесты и
`docs/superpowers/reports/2026-09-28-solver-baseline.md`.

**Шаги:**

1. Снять cold/warm время по семействам и размеру пакета; отдельно измерить
   время до первого actionable результата.
2. На основе baseline отключить дублирующие профили, дорогостоящие профили без
   прироста и повторный разбор одинакового hash.
3. Сохранить детерминированный порядок результатов при параллельной работе;
   тестировать лимиты на большом архиве и timeout каждого процесса.

**Критерий приёмки:**

- Ускорение подтверждено на одном и том же замороженном корпусе при том же
  точном счёте и том же false-positive rate.
- Снижение времени не достигается пропуском известных успешных обработчиков.

### P5. Выпускная проверка

**Файлы:** обновить `README.md` и итоговый отчёт; код менять только при найденном
дефекте.

Перед заявлением о готовности повторить `./verify.sh`, known-pack regression,
полный 15-slot blind набор и доступные независимые внешние корпуса. В README
развести три утверждения: результаты синтетических regression tests, локально
воспроизведённые кандидаты и независимые hash/checker-подтверждённые решения.

**Целевой результат:** 10+ из 15 на challenge-shaped blind holdout с 0 ложных
значений в actionable списке, без регрессии известных корпусов. Это целевой
порог разработки, а не обещание получить столько же на незнакомом соревновании.

## Правила отбора следующих улучшений

Для каждого предложения оценить:

`ожидаемые новые подтверждённые задачи / (разработка + runtime + сопровождение)`.

Высокий приоритет получают повторяемые gaps с полными входными артефактами и
недорогим детерминированным решением. Низкий — новая зависимость без конкретной
пропущенной задачи, активная сеть без тестового локального сервиса, общий
генератор произвольных преобразований и фичи, измеряемые только числом строк
или количеством установленных программ.

## Границы

- Не угадывать флаг перебором и не использовать blind wordlists.
- Не обращаться к инфраструктуре соревнования в file-only режиме.
- Не запускать challenge-бинарники на host-машине.
- Не объявлять флаг подтверждённым по формату строки, README, write-up,
  синтетической фикстуре или созданному payload.
- Не включать закрытые ответы, приватные manifest и пользовательские секреты в
  репозиторий или отчёты.
